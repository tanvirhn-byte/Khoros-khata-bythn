2. TIER RESPONSIBILITIES
================================================================================

A. Frontend (index.html):
- Renders the responsive user interface (Home, Expenses, Reports, Categories, Settings).
- Maintains local application state (S) in browser localStorage (kh_s).
- Optimistic updates: all actions (add, edit, delete) take effect locally in 0ms.
- Tracks local changes using a dirty flag (_d = 1) and skew-adjusted timestamps.
- Manages local PIN lock and inactivity timer.
- Handles Service Worker registration for PWA installability.
- Detects runtime environment (Browser vs Capacitor) to resolve API Base URL.

B. Backend API (api.php):
- Stateless request processor for JSON operations.
- Enforces CORS policies for cross-origin Android WebView requests.
- Authenticates API tokens and validates token expiration.
- Enforces multi-tenant data isolation by binding all queries to authenticated user_id.
- Executes incremental two-way data sync inside atomic transactions.
- Provides system configuration, broadcast notices, and polling endpoints.

C. Admin Dashboard (admin.php):
- Completely isolated from normal user API endpoints.
- Authenticates using PHP session cookies with CSRF token verification.
- Provides administrative management: user approvals, account suspension, notices,
  system error inspection, visitor metrics, and database downloads.

D. Database (data/khoroch.sqlite):
- Embedded relational persistence via PDO SQLite.
- Stores user accounts, active tokens, sync revisions (rev), expense records,
  categories, category groups, preferences/budgets, and audit logs.
- Operates in WAL (Write-Ahead Logging) mode for concurrent reads and writes.

E. Hosting & Web Server (cPanel / Apache):
- Enforces HTTPS on custom domains.
- Evaluates .htaccess to prevent directory indexing and block direct access to /data.
- Serves static assets (HTML, JS, PNG icons, Manifest).

3. API COMMUNICATION & BASE URL STRATEGY
================================================================================

A. Problem Statement:
- On Web (cPanel), index.html and api.php live in the same directory.
  Calling 'api.php?a=...' works out of the box.
- In Capacitor Android, index.html is loaded locally from 'http://localhost/'
  or 'capacitor://localhost/'. Calling 'api.php?a=...' will resolve to
  'http://localhost/api.php', which does not exist inside the APK.

B. Base URL Resolution Strategy:
We will introduce a clean, zero-dependency configuration helper in index.html:

  const API_CONFIG = {
    // Leave empty for auto-detect (uses current domain on web)
    // For Android APK, this points to your deployed production domain:
    REMOTE_URL: 'https://yourdomain.com/api.php',
    
    getBaseUrl() {
      // If running inside Capacitor Android or custom remote origin:
      const isCapacitor = window.Capacitor !== undefined || 
                          window.location.protocol === 'capacitor:' || 
                          window.location.hostname === 'localhost';
      if (isCapacitor && this.REMOTE_URL && !this.REMOTE_URL.includes('yourdomain.com')) {
        return this.REMOTE_URL;
      }
      // Running on standard website / cPanel:
      return 'api.php';
    }
  };

C. Centralized API Dispatcher:
Replace scattered fetch() calls with a single helper: apiUrl(action):
  function apiUrl(action) {
    const base = API_CONFIG.getBaseUrl();
    const sep = base.includes('?') ? '&' : '?';
    return `${base}${sep}a=${encodeURIComponent(action)}`;
  }

D. CORS & Preflight Implementation in api.php:
Android WebView requests from Capacitor will send:
  Origin: http://localhost  OR  capacitor://localhost
api.php must handle preflight:
  - Respond to OPTIONS requests with HTTP 204 No Content immediately.
  - Set Access-Control-Allow-Origin: * (or dynamic origin reflecting Android schemes).
  - Set Access-Control-Allow-Methods: POST, GET, OPTIONS.
  - Set Access-Control-Allow-Headers: Content-Type, Authorization, X-Requested-With.

4. DATABASE DEPLOYMENT & PROTECTION STRATEGY
================================================================================

A. Engine & Concurrency:
- SQLite 3 via PHP PDO (pdo_sqlite).
- WAL mode (PRAGMA journal_mode=WAL;) allows readers to proceed without blocking
  writers, and writers do not block readers.
- PRAGMA busy_timeout=8000; ensures queries wait up to 8 seconds during write locks.
- Application-level exponential backoff retry loop (4 attempts) in api.php handles
  heavy simultaneous write bursts.

B. Multi-Layer Database Protection:
1. Apache / cPanel Layer:
   data/.htaccess contains:
     <IfModule mod_authz_core.c>
       Require all denied
     </IfModule>
     <IfModule !mod_authz_core.c>
       Order allow,deny
       Deny from all
     </IfModule>
2. PHP Directory Guard:
   data/index.html (placeholder) prevents directory listing.
3. Server-Level Protection Rule:
   In api.php, block any request attempting to pass 'data/' directly.
4. Backup Procedure (Mobile & cPanel Friendly):
   - In cPanel File Manager: Right click data/khoroch.sqlite -> Copy or Download.
   - In Admin Panel: 1-click database download button in admin.php.

5. AUTHENTICATION & MULTI-DEVICE SYNC ARCHITECTURE
================================================================================

A. Authentication Protocol:
1. Registration (?a=register):
   - Validates email and minimum 8-character password.
   - Enforces IP rate limiting (max 5 accounts per hour per IP).
   - Hashes password with standard Bcrypt/Argon2 (PASSWORD_DEFAULT).
   - Generates 64-character cryptographically secure token (random_bytes(32)).
   - Stores SHA-256 hash in tokens table.
2. Login (?a=login):
   - Validates email/password with password_verify().
   - Enforces IP brute-force protection (max 5 failures per 15 min per IP).
   - Checks account status (pending approval, blocked, active).
   - Returns authentication token on success.
3. Token Expiration (Essential Security Fix):
   - Currently, tokens never expire.
   - FIX: Enforce 90-day inactivity timeout on tokens:
     WHERE token_hash = ? AND created > (time() - 90 * 86400)
     Update token created timestamp on active sync to implement rolling session.
4. Server-Side Logout (?a=logout) (Essential Security Fix):
   - Add ?a=logout endpoint:
     DELETE FROM tokens WHERE token_hash = ?
   - Frontend logout() will call ?a=logout before clearing local storage.
5. Token Transmission Security:
   - Discontinue accepting tokens via $_GET['token'].
   - Accept tokens ONLY in JSON POST body or Authorization: Bearer header.
   - Eliminates token leakage in web server access logs and browser history.

B. Two-Way Synchronization Architecture:
- Client holds revision pointer: S.since (last synced revision).
- Server holds user revision pointer: users.rev (incremented on each atomic write).
- Clock Skew Compensation (SK):
  On sync response, server returns current epoch milliseconds (now).
  Client computes SK = serverNow - localNow and offsets timestamps to guarantee
  causality even if the user's phone clock is incorrect.
- Last-Write-Wins Conflict Resolution:
  When pushing changes, server queries existing updated timestamp:
  SELECT updated FROM table WHERE user_id=? AND id=?
  Incoming write is accepted ONLY if incoming.updated > existing.updated.
- Incremental Pull:
  Server selects all records for user where rev > S.since, plus final state of
  items pushed in the current batch.
- Batch & Payload Caps:
  Max 400 records per sync batch; max 2.5MB payload size. If more records remain,
  server signals more: true and client continues immediately.
