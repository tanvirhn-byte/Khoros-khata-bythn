A. FRONTEND ARCHITECTURE (index.html)
--------------------------------------------------------------------------------
- Structure:
  Monolithic single file. No build step (no Vite/Webpack required on cPanel).
  HTML markup, CSS rules, and JavaScript logic are bundled together. All dynamic
  views are constructed using template literals and DOM innerHTML.
- Styling & Themes:
  Clean CSS custom variables (--bg, --card, --ink, --ac, --ac2).
  Automatic dark/light mode via prefers-color-scheme, plus manual toggle
  (:root[data-theme="dark"]).
  Mobile-first layout with safe area padding: env(safe-area-inset-top).
- Navigation:
  Sticky header with group selector, 5-tab bottom navigation bar:
  (1) Home (হোম)
  (2) Expenses (খরচ)
  (3) Reports (রিপোর্ট)
  (4) Categories (ক্যাটাগরি)
  (5) Settings (সেটিংস)
  Includes a floating action button (FAB) for adding new transactions.
- Forms & Modals:
  Custom modal dialogs (#cm for confirmations, #sf for expense entry,
  and #ask for input prompts). Form validation triggers immediate visual toasts.
- Performance:
  Extremely lightweight and fast on mobile devices due to low DOM overhead
  and lack of heavy JavaScript libraries.
- Limitations:
  Hardcoded relative paths ('api.php?a=...') break when running inside
  Capacitor on Android. Missing ARIA attributes on some interactive dialogs.


B. BACKEND ARCHITECTURE (api.php)
--------------------------------------------------------------------------------
- Architecture:
  Single-file procedural PHP API. Dispatches actions using query parameter ?a=.
- HTTP Protocol & Methods:
  All state-changing actions use POST with JSON body payloads.
  Inconsistency: tokens are accepted in both POST body and $_GET['token'].
- Endpoints Implemented:
  * ?a=health   -> GET/POST health probe returns {"ok": true}.
  * ?a=register -> User registration with password hashing and IP rate limiting.
  * ?a=login    -> User authentication with rate limiting and status checks.
  * ?a=config   -> System announcements, notices, social links, and visitor ping.
  * ?a=ping     -> Lightweight revision check for incremental updates.
  * ?a=sync     -> Two-way incremental sync with last-write-wins conflict resolution.
  * ?a=passwd   -> Current user password change and token invalidation.
  * ?a=delacct  -> Account deletion requiring password and universal delete code.
  * ?a=report   -> SQL recursive category aggregation (not currently called by frontend).
- Critical Finding — CORS Support Missing:
  api.php contains ZERO CORS headers (Access-Control-Allow-Origin) and does
  not handle OPTIONS preflight requests. In Capacitor Android (where origin is
  http://localhost or capacitor://localhost), network requests will be blocked.
- Authentication & Tokens:
  Uses 64-character random hex tokens hashed via SHA-256 in the tokens table.
  Bug: Tokens have no expiration time. The tokens table has a 'created' field,
  but verification queries never check age.
- Logout Limitation:
  Frontend logout() deletes local token from localStorage but does NOT call
  the server to delete the token from the tokens table. There is no ?a=logout.
- Error Handling:
  display_errors is disabled (0). Errors are appended to data/error.log.
  Client receives a generic JSON 500 error, preventing sensitive data leaks.


C. DATABASE ARCHITECTURE (SQLite via PDO)
--------------------------------------------------------------------------------
- Database Engine: SQLite 3 via PDO (pdo_sqlite).
- Concurrency Configuration:
  * WAL mode active: PRAGMA journal_mode=WAL;
  * Busy timeout: PRAGMA busy_timeout=8000;
  * Application-level retry loop (up to 4 attempts) for database contention.
- Tables & Schema (PRAGMA user_version = 6):
  * users: id (PK), email (UNIQUE), hash, rev, created, synced, status
  * tokens: token_hash (PK), user_id, created
  * groups_: user_id, id, name, updated, deleted, rev (PK: user_id, id)
  * categories: user_id, id, group_id, parent, name, updated, deleted, rev (PK: user_id, id)
  * expenses: user_id, id, group_id, amount, date, time, descr, note, updated, deleted, rev (PK: user_id, id)
  * expense_categories: user_id, expense_id, category_id (PK: user_id, expense_id, category_id)
  * prefs: user_id, id, v, updated, deleted, rev (PK: user_id, id)
  * settings: k (PK), v
  * logs: id (PK), t, type, who, ip
  * visits: day, vid, hits, last, plat (PK: day, vid)
- Indexes:
  * ix_logs ON logs(type, ip, t)
  * ix_exp ON expenses(user_id, group_id, date)
- Foreign Keys:
  PRAGMA foreign_keys = ON is NOT enabled. Referential integrity is handled
  at application level.
- Multi-User Isolation:
  Every query on user tables strictly filters by user_id = ?. User A cannot
  query or modify User B's records.
- SQLite vs MySQL Suitability:
  SQLite + WAL is completely appropriate and recommended for this project.
  It is zero-maintenance on cPanel, cannot crash independently from PHP, and
  allows instant backups simply by copying data/khoroch.sqlite. No MySQL migration
  is needed.

F. SECURITY AUDIT
--------------------------------------------------------------------------------
1. SQL Injection:
   PROTECTED. PDO prepared statements with bound parameters used throughout.
2. Cross-Site Scripting (XSS):
   PROTECTED. Frontend utilizes esc() helper; admin.php utilizes htmlspecialchars().
3. Cross-Site Request Forgery (CSRF):
   Admin panel is protected with CSRF tokens. API relies on JSON POST bodies.
4. Token & Session Management:
   VULNERABILITY: Tokens in 'tokens' table never expire.
   VULNERABILITY: Logout does not revoke token on server.
   RISK: api.php accepts token from $_GET query string, risking server log exposure.
5. Database Protection:
   Protected on Apache via data/.htaccess.
   RISK: On NGINX or static web servers, data/khoroch.sqlite is directly exposed.
6. Hardcoded Credentials:
   Default DELETE_CODE = 'TanvirX' and ADMIN_PASS = 'CHANGE_ME_NOW' in source code.
7. Rate Limiting:
   Active on login failures (5 per 15 min) and registrations (5 per hour per IP).


G. CAPACITOR & ANDROID APK READINESS AUDIT
--------------------------------------------------------------------------------
1. API URL Configuration:
   index.html hardcodes relative 'api.php' calls. Must be refactored to support
   a configurable API_BASE_URL (remote domain for APK, relative for web).
2. CORS Headers:
   api.php must add Access-Control-Allow-Origin, Headers, and OPTIONS handler.
3. Android Hardware Back Button:
   Needs listener to close active modals/sheets rather than killing the app.
4. Status Bar & Splash Screen:
   Requires Capacitor StatusBar and SplashScreen plugin configuration.
