2. AUDIT FINDINGS & FIXES APPLIED
--------------------------------------------------------------------------------
Finding #1 — Admin Session Isolation & Cookie Hardening (`admin.php`)
- Prior State: Used PHP's default session cookie name (`PHPSESSID`), did not set
  `session.use_strict_mode=1` or `session.use_only_cookies=1`, and checked only
  `!empty($_SERVER['HTTPS'])` (missing reverse-proxy `X-Forwarded-Proto: https`).
- Fix Applied: Configured `session_name('KH_ADMIN_SESS')`, enabled
  `session.use_strict_mode=1`, `session.use_only_cookies=1`, and
  `session.cookie_httponly=1`, and set cookie parameters (`HttpOnly`,
  `SameSite=Strict`, `Secure` when HTTPS or `X-Forwarded-Proto: https` or port
  443 is active).

Finding #2 — Admin Session Fixation, Idle Timeout & Logout Destruction (`admin.php`)
- Prior State: `session_regenerate_id(true)` was called on login, but sessions
  lacked idle timeout, absolute lifetime, or User-Agent binding, and logout only
  called `session_destroy()` without clearing `$_SESSION` or expiring the
  `KH_ADMIN_SESS` cookie in the browser.
- Fix Applied:
  * On login: Rotates session ID via `session_regenerate_id(true)` and stores
    `admin_auth=true`, `created_at`, `last_active`, `ua_hash` (SHA-256 of
    `HTTP_USER_AGENT`), and a 256-bit `csrf` token (`bin2hex(random_bytes(32))`).
  * On every request: Enforces a 30-minute idle timeout (`1800s`), 12-hour
    absolute session lifetime (`43200s`), and User-Agent hash verification.
    Expired or mismatched sessions are immediately destroyed via
    `destroyAdminSession()` and redirected to the login screen.
  * On logout (`act=logout`): Calls `destroyAdminSession($isHttps)` which clears
    `$_SESSION = []`, expires the `KH_ADMIN_SESS` cookie (`expires = time()-3600`),
    and invokes `session_destroy()`.

Finding #3 — CSRF Protection on Sensitive GET Exports & Login (`admin.php`)
- Prior State: `POST` actions checked `$_SESSION['csrf']`, but sensitive `GET`
  export routes (`?cfgdl=1`, `?usercsv=1`, `?dbdl=1`) did NOT verify CSRF tokens,
  and invalid CSRF on `POST` returned HTTP 200/302 instead of HTTP 403.
- Fix Applied:
  * Added strict `hash_equals($_SESSION['csrf'], ...)` verification to `?cfgdl=1`,
    `?usercsv=1`, and `?dbdl=1`, returning HTTP 403 if the token is missing or
    invalid, and updated the Admin Panel export links to include `&csrf=$cs`.
  * Enforced HTTP 403 on any `POST` action with a missing or invalid CSRF token.
  * Added pre-login CSRF token (`$_SESSION['login_csrf']`) validation to the
    admin login `POST` form.
  * Unauthenticated `POST` or export (`?cfgdl`, `?usercsv`, `?dbdl`) requests
    now explicitly return HTTP 403 before halting at the login screen.

Finding #4 — Credential & Secret Protection (`admin.php`)
- Prior State:
  * `adminOk($pw)` used `password_verify()` only after the admin manually changed
    the password in the Settings tab; initial logins against the bootstrap
    `ADMIN_PASS` constant remained unhashed in `settings`.
  * Line 650 embedded the plaintext `delete_code` inside an HTML attribute
    (`data-v="..."`) on the Admin Panel page.
  * `display_errors` was not explicitly disabled in `admin.php`.
- Fix Applied:
  * Updated `adminOk($pw)` so that when a valid bootstrap login occurs, it
    automatically hashes the password with `password_hash($pw, PASSWORD_DEFAULT)`
    and persists `admin_hash` in SQLite `settings`, ensuring `password_verify()`
    is always used.
  * Removed `data-v` plaintext `delete_code` exposure from the DOM and changed
    the update input to `type="password"`.
  * Added `ini_set('display_errors', '0')`, custom error/exception handlers that
    never leak internal file paths or SQL queries in HTTP responses, and
    redaction of sensitive keys/paths in the Overview error log viewer.

Finding #5 — Prepared Statements & Database/File Access Protection (`admin.php`, `api.php`, `.htaccess`, `data/`)
- Prior State: Line 488 of `admin.php` concatenated `LIMIT $per OFFSET ...` in
  the logs query instead of binding parameters.
- Fix Applied:
  * Parameterized the logs pagination query (`LIMIT ? OFFSET ?`).
  * Added `public/khoroch/.htaccess` (and mirrored `khoroch/.htaccess`) with
    `<FilesMatch "\.(sqlite|sqlite3|sqlite-wal|sqlite-shm|db|log|bak|sql)$">`
    deny rules and `RewriteRule ^data(/|$) - [F,L]`.
  * Added `public/khoroch/data/index.php` (and mirrored `khoroch/data/index.php`)
    returning HTTP 403 Forbidden, and updated both `api.php` and `admin.php` to
    auto-create `data/.htaccess` and `data/index.php` if missing.

3. ADMIN AUTHENTICATION, SESSION, AUTHORIZATION & CSRF SUMMARY
--------------------------------------------------------------------------------
- Admin Authentication & Session Security:
  * Isolated session name (`KH_ADMIN_SESS`) separate from normal-user Bearer
    token authentication (`tokens` table in `api.php`).
  * `session_regenerate_id(true)` on login; 30-minute inactivity timeout;
    12-hour absolute timeout; User-Agent hash binding; complete cookie + session
    destruction on logout.
  * Per-IP and global brute-force lockout (5 failed attempts within 10 minutes
    + 800ms delay per failed attempt).
- Server-Side Authorization & Separation:
  * Every admin view, setting mutation, notice operation, user management action,
    and file export is gated on the server by `$_SESSION['ok'] && $_SESSION['admin_auth']`.
  * Normal-user Bearer tokens are never accepted by `admin.php`, and `api.php`
    exposes zero endpoints capable of modifying admin settings or notices.
  * `api.php?a=config` returns only public display metadata (`notices`, `social`,
    `socmode`, `poll`, `welcome`, `brand`, `maint`) and never exposes
    `admin_hash`, `delete_code`, `fail_n`, `fail_t`, `users`, `tokens`, or `logs`.
- CSRF & Request Integrity:
  * Cryptographic 256-bit per-session CSRF token verified via timing-safe
    `hash_equals()` on all `POST` actions AND all sensitive `GET` exports
    (`?cfgdl=1`, `?usercsv=1`, `?dbdl=1`), plus `SameSite=Strict` cookies and
    `Content-Security-Policy: frame-ancestors 'none'; form-action 'self'`.

4. ADMIN NOTICE & ANNOUNCEMENT SECURITY SUMMARY
--------------------------------------------------------------------------------
- Reuses the existing Notice Page (`data-t="notice"`) in `admin.php` and the
  existing `settings('notices')` JSON array in SQLite.
- Only authenticated admins with a valid `KH_ADMIN_SESS` session and valid CSRF

7. REMAINING RISKS OR DEPLOYMENT REQUIREMENTS
--------------------------------------------------------------------------------
1. Set a Strong Initial Admin Password Before Production Deployment:
   `admin.php` ships with `const ADMIN_PASS = 'CHANGE_ME_NOW';` which safely
   refuses to unlock the panel until changed. Before deploying to production,
   set a strong password in `ADMIN_PASS`, log in once (which automatically stores
   a `password_hash()` in SQLite `settings('admin_hash')`), or change the
   password immediately via the Admin Panel Settings tab.
2. Web Server Rules on Non-Apache Hosts:
   `.htaccess` rules are automatically enforced by Apache/LiteSpeed. If deploying
   on Nginx, configure `location ~ ^/khoroch/data/ { deny all; return 403; }` and
   `location ~ \.(sqlite|sqlite-wal|sqlite-shm|log)$ { deny all; return 403; }`
   in the Nginx server block.
