2. DATA-INTEGRITY EDGE CASE AUDIT & DETERMINATIONS
--------------------------------------------------------------------------------
Point 1: Does the application support legitimate expenses without a group_id?
- Determination: NO. The application enforces a strict hierarchical data model
  where groups are mandatory parent containers for all transactions.
  - Client Initialization: The app automatically seeds a default group (`g-main`,
    "Full College Life") on first run.
  - Mandatory Group Rule: The UI explicitly prevents deleting the last remaining group:
    `if(S.parents.filter(p=>!p.deleted).length < 2) return toast('অন্তত একটি গ্রুপ থাকতে হবে');`
  - Transaction Creation: The expense form (`openForm` / `sv`) binds every expense to
    the active group: `o = { pid: cur, ... }`. There is no "No Group" UI option.
  - Queries & Views: All dashboard summaries, transaction lists, budgets, and reports
    filter strictly by active group: `exps = () => S.exps.filter(e => e.pid == cur && !e.deleted)`.
  - Backend Report Endpoint: `api.php?a=report` strictly mandates a valid `group` ID.

Point 2: Effect of resetting invalid/foreign group_id to ''
- Determination: Because the frontend does not support ungrouped expenses, resetting
  an invalid or foreign group ID to `''` causes functional data loss:
  - An expense with `group_id = ''` is stored as an orphaned record in the database.
  - When synced to client storage, `e.pid` is `''`.
  - Because `cur` is always a valid non-empty group ID (e.g., `'g-main'`), `e.pid == cur`
    will NEVER match.
  - The transaction disappears completely from the user's dashboard, list view, and reports.
  - The user can neither view, edit, search, nor delete the orphaned record.
  - Therefore, silent fallback to `''` is an unsafe anti-pattern that corrupts user experience.

Point 3: Safe Rejection of Invalid/Foreign Group Expenses
- Architectural Decision & Implementation:
  - Since groups are mandatory, `api.php` safely REJECTS invalid, foreign, or ungrouped
    expenses instead of silently saving them with `group_id = ''`.
  - Active expenses without a verified, owned group in `$groupSet` are skipped completely
    (`continue;`). They are never inserted into `expenses` or `expense_categories`.
  - Existing Expense Deletions (`deleted = 1`): If a user deletes an existing expense,
    the tombstone is updated while preserving the original verified `group_id`.
  - Categories: Categories with invalid/foreign group IDs are similarly rejected safely.


3. FRONTEND SYNC-REJECTION HANDLING & DATA PRESERVATION
--------------------------------------------------------------------------------
Issue Diagnosed in Existing Frontend:
Previously, upon receiving any sync response, the client ran:
  `[S.parents,S.cats,S.exps,S.prefs].forEach(a=>a.forEach(x=>{if(x._d&&snap.get(x.id)===x.updated)delete x._d}));`
This blindly cleared `_d` on every sent item, even if the backend rejected it and
omitted it from the response. The local item was falsely marked as successfully synced,
stopping future retries and causing data loss if local cache was cleared or fullSync ran.

Frontend Corrections Applied (`index.html`):
1. Selective `_d` Clearance:
   `delete x._d` is now guarded strictly by server confirmation:
   `if (confE.has(x.id)) { delete x._d; delete x._rej; } else { x._rej = 1; rejCount++; }`
   Rejected items NEVER lose their `_d = 1` dirty flag.
2. Local Data Preservation:
   Rejected expenses are never removed from `S.exps` or LocalStorage. They remain 100%
   safe locally.
3. User Visibility & Indicator:
   - In `exps()`: Rejected pending expenses remain visible in active views:
     `exps = () => S.exps.filter(e => (e.pid == cur || (e._rej && !e.deleted)) && !e.deleted)`.
   - In `eitem()`: A prominent badge (`গ্রুপ প্রয়োজন`) is displayed on rejected expenses.
   - Header Dot: `dot('err')` turns the sync indicator to "সমস্যা" (amber/red).
   - Toast Alert: Informs user:
     `সতর্কতা: Nটি খরচের গ্রুপ সঠিক না থাকায় সিঙ্ক হয়নি। খরচ এডিট করে গ্রুপ ঠিক করুন।`
4. Recovery Flow:
   When the user clicks `✎ এডিট`, `sv(id)` rebinds the expense to the active group (`cur`),
   clears `_rej`, and triggers sync. The expense is immediately accepted and synced.
5. Polling Throttle:
   `ping()` avoids repeated background sync spam if all pending items are flagged as
   rejected and awaiting user recovery.
