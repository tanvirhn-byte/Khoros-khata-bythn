2. ISSUES REVIEWED & IMPLEMENTED
--------------------------------------------------------------------------------
ISSUE 1: TOKEN EXPIRATION & TIMESTAMP SEPARATION
- Policy Defined: 90-Day Inactivity Expiration Policy.
  * An active session remains valid as long as the user accesses the app at least once every 90 days.
  * If a session is inactive for > 90 consecutive days (7,776,000 seconds), it expires, is purged
    from the SQLite database, and returns HTTP 401.
- Immutable Creation Timestamp (`created`):
  * Recorded once upon token generation in `newToken()`.
  * NEVER modified or overwritten. True token provenance is permanently preserved.
- Activity Timestamp (`last_seen`):
  * Separated into its own column `tokens.last_seen`.
  * Initialized to creation time on login/registration.
  * When an authenticated request arrives, if `(now - last_seen) > 86400` (24-hour throttling to
    prevent write amplification and SQLite disk lock contention), `last_seen` is updated to `now`.
- Safe, Non-Destructive Schema Evolution:
  * Table schema updated: `CREATE TABLE IF NOT EXISTS tokens(token_hash TEXT PRIMARY KEY, user_id INTEGER, created INTEGER, last_seen INTEGER);`
  * Dynamic non-destructive check added: `if (!in_array('last_seen', $tcols)) $db->exec('ALTER TABLE tokens ADD COLUMN last_seen INTEGER');`
  * If `last_seen` is null/0 on legacy tokens, code falls back safely to `created`.

ISSUE 2: LOGOUT & SEND BEACON BEHAVIOR
- Normal Logout Awaits Server Response:
  * Client-side `logout(f)` now synchronously `await`s `fetch(apiUrl('logout'))` with Bearer auth header and POST payload.
  * Local session state (`tok = null`, `localStorage.removeItem('kh_t')`, in-memory store) is cleared ONLY AFTER
    the server response is received (or caught on network error).
- Server Multi-Format POST Token Reading:
  * `api.php` extracts tokens from:
    1. `Authorization: Bearer <token>` header (primary standard)
    2. `json_decode(file_get_contents('php://input'))['token']` (JSON fetch and sendBeacon Blob)
    3. `$_POST['token']` (FormData and URL-encoded POST)
  * All tokens are strictly regex-validated (`^[A-Za-z0-9_-]{32,128}$`).
- Best-Effort Fallback Clarification:
  * If network drops or aborts during logout, `navigator.sendBeacon(apiUrl('logout'), blob)` is triggered as best-effort.
  * Explicitly acknowledged: `sendBeacon` cannot guarantee execution during abrupt OS termination (process kill,
    task swipe-away, kernel OOM kill, sudden power loss). The 90-day inactivity expiration ensures abandoned tokens
    safely expire server-side.

5. REMAINING RISKS & LIMITATIONS
--------------------------------------------------------------------------------
1. Best-Effort Nature of sendBeacon on Mobile:
   - On mobile devices (Android/iOS), if the user swipes away the app from the task switcher or the OS kills
     the process for memory, JavaScript cannot run and no network packet is dispatched.
   - This is normal browser/OS behavior. Security is maintained because:
     * Unused sessions automatically expire server-side after 90 days of inactivity.
     * Normal in-app logout synchronously revokes the token server-side.
2. Production HTTPS:
   - Bearer headers and POST credentials require HTTPS/TLS on production hosting (cPanel AutoSSL / Let's Encrypt).
